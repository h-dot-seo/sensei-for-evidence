# Guideline and development context before extraction

A researcher can now record source-review context before producing any result
rows. This avoids inventing evidence IDs just to connect guideline applicability
questions or development assumptions to planned research work.

Set `context_scope: "source_review"`, supply `evidence_ids: []`, and use nonempty
typed `source_refs`. Keep the existing context provenance, domain-specific fields,
applicability and limitations. Unknown or unassessed values are supplied text,
not judgments generated by the tool.

This is a source link, not extracted evidence, eligibility, a guideline
recommendation, validated clinical applicability, regulatory status or a
development milestone. A supplied `reviewed` label remains an operator assertion.
In the new source scope, any supplied reviewer must be nonblank and any supplied
review date must be a valid YYYY-MM-DD date, including while status is pending.
Supplying those fields does not change pending status or imply that review occurred.

## Try the entirely fictional example

```sh
python work_review.py examples/source-context-protocol.json --work-package WP-GUIDELINE-SOURCES --text
python work_review.py examples/source-context-protocol.json --brief
python review_handoff.py examples/source-context-protocol.json --text
python prisma_audit.py examples/source-context-protocol.json --text
python compare_runs.py examples/source-context-protocol.json examples/source-context-protocol.json --text
python research_bundle.py create examples/source-context-protocol.json /outside/new-source-context.zip
python research_bundle.py verify /outside/new-source-context.zip
```

Use a new local output path outside this public repository. The example has no
extracted results or studies. It retains one pending record, one excluded record,
an incomplete supplied search and a second planned search with no execution.
Neither context changes any of those states. The development context's fictional
reviewed label does not fill the missing search or remove its limitations.

## Exact typed source links

Supported references have exactly these shapes:

```json
{"kind": "planned_search", "search_id": "local-primary"}
{"kind": "record", "record_id": "synthetic-r1"}
```

A planned-search reference must name a declared search, even if it has not yet
executed. A record reference must name a record enumerated in a supplied search;
it may still be unscreened or excluded. Unknown, duplicate, empty or extra-field
references are rejected. The shared validator is also used by source-review work.

Source contexts can be unassigned. To attach one through a work package's
`context_ids`, that work must have `work_type: "source_review"` and share at least
one identical `(kind, ID)` reference. A search ID and a record ID with the same
text do not match. A record's membership in a search does not implicitly connect
their context references. Source→record→result and report→study inheritance are
not inferred.

Detailed work packets and handoffs show shared references, other context
references and other work references separately. Brief navigation lists exact
shared source-context links. The fictional guideline example shares only the
planned-search reference; its other record reference does not silently become
part of the work package.

## Evidence contexts stay separate

Omitting `context_scope` preserves existing extracted-evidence behavior: a context
must link to nonempty known `evidence_ids`. Explicit `extracted_evidence` expresses
the same scope. No default scope or empty source-reference list is injected into
legacy normalized context rows, so existing planning and synthesis bindings do
not change merely because this feature exists.

`source_refs` is now reserved for explicit source scope. Previously it could be
retained as ignored opaque metadata on an evidence context; that ambiguous use is
now rejected. Unknown scope values also fail rather than silently falling back.

Source contexts require empty `evidence_ids` and always have empty derived
`linked_study_ids`. Later extracting a result from a referenced record does not
upgrade its context scope. Source contexts cannot be attached to evidence-review
work or synthesis statements. If a human later decides that context applies to
extracted results, they must supply a separate or explicitly revised evidence
context and review its links; the software performs no automatic promotion.

## Binding, comparison and accounting

Existing planning/completion bindings include the full linked context, so edits
to source references, applicability, limitations or review assertions can make
supplied work bindings stale. Their shared source scope also binds search plans,
searches, screening and reports. Staleness is a content-change cue, not a decision
that the context is clinically invalid or that completed work must reopen.

Focused context comparison displays explicit source-reference intersections in
each linked-work snapshot. It continues to compare context assertions, linked
result rows and explicit work assertions only. Changes in underlying searches,
receipts, screening or reports are outside that focused context view: inspect the
full comparison and work binding states. An unchanged context comparison is not
proof that the underlying source or its recorded review remains current.

PRISMA audit adds a separate `source_context_ledger` containing context pointers
and explicitly linked work IDs. It does not turn context references into implicit
work coverage, included records, extracted results, reports or studies, and all
existing count partitions retain their meaning. Bundles preserve the context and
work metadata. Source authenticity, clinical applicability, completeness and
scientific conclusions remain unverified. Only generic code and synthetic examples
are included; keep real source material and research outputs private.

For append-only recording without hand-editing the protocol, use the
[reviewed context intake](MANUAL_CONTEXT_INTAKE.md). New contexts remain unassigned;
import approval is separate from context applicability and its own review status.
